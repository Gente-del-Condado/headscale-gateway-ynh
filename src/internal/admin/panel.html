      Políticas ACL y Grants de Headscale
      Controla qué nodos y usuarios pueden acceder a cada servicio. Headscale es quien valida y aplica la política.
      

      La edición remota requiere policy.mode: database en Headscale. En modo archivo puedes leer, pero para modificar debes editar el archivo en YunoHost y recargar Headscale.
      

      Atención: una política vacía o {} puede permitir todo el tráfico. Una política {"grants": []} deniega todo. Revisa cuidadosamente las reglas antes de aplicarlas.
      

      No existe una política ACL en la base de datos de Headscale.
      Headscale usa actualmente sus permisos predeterminados. Puedes crear una política inicial explícita sin perder las reglas existentes, porque todavía no hay ninguna almacenada.
      

      

      

      Cómo funciona: añade grupos y reglas, comprueba el resumen y pulsa «Validar y aplicar» solo cuando estés conforme. Nada se envía a Headscale al editar. Las reglas Grants recomiendan usar las identidades de Headscale, no necesariamente los grupos LDAP de Dex.

      Sincronización con Headscale en YunoHost
      

      Configura dns.extra_records_path en el YAML de Headscale con un archivo JSON que puedas actualizar sin reiniciar. Envía el JSON descargado al VPS y reemplaza ese archivo de forma atómica, preservando otros registros si existen.

      Nameservers y Split DNS
      

      Headscale configura Global Nameservers, Split DNS, search_domains y override_local_dns en su propio config.yaml; no disponemos de una API REST v1 general para guardar estos parámetros. Puedes utilizar Technitium como DNS de la tailnet y reservar MagicDNS para nombres de equipos.
      

      Configura en Headscale la IP real de Technitium que puedan alcanzar los clientes. No configures 100.100.100.100 como servidor DNS global aguas arriba: es el resolvedor local de MagicDNS de cada cliente.

      Cuenta local
      

      LDAP de YunoHost
      Utiliza LDAPS verificado, no LDAP sin cifrar. Para un Gateway fuera del VPS se recomienda Dex/OIDC en lugar de abrir puertos LDAP.
      

      OpenID Connect
      Admite Dex, Google, Authelia y otros proveedores OIDC con HTTPS. Solo se activa un proveedor principal a la vez. El 2FA se configura en el proveedor de identidad.
      Dex puede emitir el grupo vpn. Google normalmente no entrega grupos: autoriza un correo verificado y asígnale un rol en Permisos por correos.
      

      Permisos por correos OIDC (opcional)
      Permite usar proveedores sin claim groups, como Google. Una asignación por línea: cuenta@example.org=admin. Exige también incluir el mismo correo en Correos autorizados. No se otorgan permisos automáticamente.
      Permisos por grupos
      Una asignación por línea: grupo=admin, grupo=operator o grupo=viewer. LDAP requiere grupos; OIDC admite grupos o correos verificados con rol explícito. No se concede automáticamente el rol admin.
      

      Guardar invalida las sesiones existentes: tendrás que iniciar sesión de nuevo. Verifica el acceso Dex o LDAP antes de deshabilitar métodos de recuperación.
      

      

      Credencial de recuperación administrativa
      El token de recuperación funciona aunque Dex no esté disponible. Si lo pierdes, puedes recuperarte por SSH con --reset-recovery y el código temporal local. Rota el token actual para revocarlo inmediatamente; el nuevo se muestra una sola vez. Solo admite una sesión administrativa interactiva, no tokens Bearer.

      Rotación y ubicación de logs
      Se aplica inmediatamente y se guarda en SQLite. Los archivos tienen permisos 0600; el directorio se crea con 0700. Al cambiar de directorio, los archivos anteriores no se eliminan automáticamente.

      El proxy no guarda respuestas HTTP en caché de disco: no existe una ruta de caché de contenido que configurar. Los certificados tienen su propio almacenamiento administrado por CertMagic; no se borra desde aquí.

      Resultado
      

      Cómo interpretar la respuesta
      200: operación completada. 202: trabajo aceptado, comprueba su estado. 400: revisa parámetros. 401: falta autenticación. 403: rol, alcance o CSRF insuficiente. 404: ruta, recurso o módulo no disponible. 409: conflicto o condición previa. 429: demasiados intentos. 502/503: dependencia o servicio no disponible.
      Un token necesita tanto un rol permitido como el alcance del módulo, y la API Bearer debe estar habilitada. Las operaciones marcadas como sesión interactiva no aceptan un token en su lugar. Las pruebas se ejecutan una vez, sin reintentos automáticos.
